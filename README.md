# Relaunch — Backend

REST API server built with Kotlin + Ktor.  
Handles coaching logic, user profiling, communication with Mistral AI, and persistence in PostgreSQL.

Frontend repo: [github.com/Lotratemi/relaunch_front](https://github.com/Lotratemi/relaunch_front)

---

## Prerequisites

- Android Studio Panda 2 (2025.3.2) or higher, with the Kotlin Multiplatform Mobile plugin enabled
- JDK 21 — provided automatically by the Gradle wrapper, no manual installation needed
- Git
- Docker Desktop (latest stable) — required to run the local PostgreSQL database for tests
- An administrator account on your machine — required to install and run Docker Desktop
- Access to the Render PostgreSQL database (ask the tech lead)
- Mistral AI API key (ask the tech lead)

## Local configuration

Secrets and local settings are stored in `local.properties` at the project root.  
This file is automatically generated by Android Studio and is already in `.gitignore` — never commit it.

Integration tests run against a **local Postgres** spun up automatically in Docker
(no external DB, no setup). Running any `test` task triggers Gradle to:

1. `startTestDb` — `docker run` a `postgres:16-alpine` container on `:5433`, schema loaded from `src/test/resources/init.sql`
2. `waitForTestDb` — poll `pg_isready` (up to 30s)
3. run the suite with `APP_MODE=test` and the `TEST_DB_*` env vars from `local.properties`
4. `stopTestDb` — remove the container

The only prerequisite is **Docker Desktop running**. The app talks to Postgres
over JDBC in every mode (`Database.run(...)`): the `DB_*` vars in production,
the `TEST_DB_*` vars under `APP_MODE=test`. Add the following keys to your
`local.properties`:

| Key | Description |
|---|---|
| `MISTRAL_API_URL` | Mistral AI base URL |
| `MISTRAL_API_KEY` | Mistral AI API key |
| `MISTRAL_AI_MODEL` | AI model name (e.g. `mistral-small-latest`) |
| `DB_HOST` | Production/dev database host (e.g. the Render Postgres host) |
| `DB_PORT` | Database port (e.g. `5432`) |
| `DB_NAME` | Database name |
| `DB_USER` | Database user |
| `DB_PASSWORD` | Database password |
| `TEST_DB_HOST` | Local test database host (e.g. `localhost`) |
| `TEST_DB_PORT` | Local test database port (e.g. `5433`) |
| `TEST_DB_NAME` | Local test database name |
| `TEST_DB_USER` | Local test database user |
| `TEST_DB_PASSWORD` | Local test database password |
| `TEST_DB_CONTAINER` | Docker container name for the test database |

The `DB_*` values (for a `./gradlew run` against a real database) and Mistral
credentials are shared privately by the tech lead.  
Test database values can be set freely — they are only used locally by Docker.  
Do not share or commit this file.

## Database

A **managed Render PostgreSQL** instance holds production and development data.  
The frontend never connects to it directly — all requests go through this backend.

The schema lives in `src/main/resources/schema.sql` and is applied
automatically at startup (`Database.initSchema()`, idempotent). To evolve it,
edit that file (and keep `src/test/resources/init.sql` in sync for tests).

---

## Running the tests

Start Docker Desktop before running the tests.  
It spins up a local PostgreSQL instance automatically initialised from `src/test/resources/init.sql`.  
This keeps test data completely isolated from the real production database.

The following Docker image is required — pull it once before running the tests for the first time:

```bash
docker pull postgres:16-alpine
```

Tests can be run from the terminal or directly from Android Studio by clicking the run icon next to any test class.

```bash
# Windows
.\gradlew.bat clean
.\gradlew.bat build
.\gradlew.bat test

# macOS / Linux
./gradlew clean build test
```

> Always use the Mistral mocks available in `src/test/` — never call the real API in tests.

## Mistral AI

The backend is the only component that calls Mistral. The frontend has no knowledge of this API.  
The model is configured via environment variables (`MISTRAL_API_URL`, `MISTRAL_API_KEY`, `MISTRAL_AI_MODEL`) and injected into `CoachService` and `ProfilingService`.

## Deployment (Render)

The backend runs on [render.com](https://render.com) as a **Docker web service**
(Runtime: Docker, Dockerfile Path: `./Dockerfile`), alongside a **managed Render
PostgreSQL** database. Both are created from the dashboard.

Create the database and the web service in the **same region** (`frankfurt`) so
the app↔DB hop stays in-zone (sub-millisecond). On the web service's
**Environment** tab, add **one** variable wired to the database via **Add from
Database**:

| Variable | Database property |
|---|---|
| `DATABASE_URL` | **Internal Connection String** |

The app parses `DATABASE_URL` (`postgresql://user:pass@host[:port]/db`, port
optional) into a clean JDBC connection. The **internal** connection string keeps
traffic on Render's private network — that's what keeps latency in-zone.

> Alternatively, the app also accepts discrete `DB_HOST` / `DB_PORT` / `DB_NAME`
> / `DB_USER` / `DB_PASSWORD` vars, but `DATABASE_URL` is one field instead of
> five and avoids mismatches (e.g. pasting the whole URL into `DB_HOST`).

On first boot the app applies `src/main/resources/schema.sql` itself (idempotent
`CREATE TABLE IF NOT EXISTS`), so a fresh database bootstraps with no manual `psql`.

Also set the Mistral secrets by hand on the same Environment tab:

| Variable | Description |
|---|---|
| `MISTRAL_API_URL` | Mistral AI base URL |
| `MISTRAL_API_KEY` | Mistral AI API key |
| `MISTRAL_AI_MODEL` | AI model name (e.g. `mistral-small-latest`) |

The `TEST_DB_*` variables and `APP_MODE` are **not** needed in production —
they only drive local integration tests.

### Outbound IP allowlist

Render routes this service's outbound traffic through a fixed set of IP ranges.
The managed Render Postgres is reached over Render's private network (no
allowlist needed), but if an upstream provider restricts access by IP (e.g.
Mistral), allowlist these ranges:

```
74.220.49.0/24
74.220.57.0/24
```

These are the backend's **outbound** (egress) IPs. The frontend talks to the
backend over its public Render URL (`https://relaunch-back.onrender.com`),
configured in the front repo at `composeApp/.../data/api/ApiClient.kt`.

## Conventions

Branches:

| Branch | Purpose |
|---|---|
| `main` | Stable code — never push directly |
| `develop` | Integration branch |
| `feat/feature-name` | New feature |

```
feat: add profiling endpoint
fix: handle null userId in coaching route
docs: update README
```

Every PR to `develop` requires approval from at least one other team member.
